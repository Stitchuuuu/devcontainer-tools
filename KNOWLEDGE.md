# Knowledge — devcontainer-tools installer internals

> Meta-knowledge about how `install.sh` v2 works, why the design
> choices are what they are, and the gotchas to remember when extending
> it. Distinct from `templates/v2/knowledge/` which is the devcontainer's
> own knowledge that the installer ships into target projects.
>
> For active session work, see [ROADMAP.md](ROADMAP.md). For the formal
> rollout plan, see [plans/devcontainer-tools-v2-migration/](plans/devcontainer-tools-v2-migration/).

## Architecture

`install.sh` is a single-file bash script (~460 LoC) with no
subcommand dispatch (v1.3 had `install` / `update` ; v2 dropped the
`update` path — `update.sh` removed).

```
main() flow :
  banner                          # 6 LoC, styled output
  resolve_target_dir              # cwd or $1 ; absolutises path
  detect_existing_devcontainer    # branches on .configured-setup VERSION
  wizard_project_id               # 1 prompt, slug-validated
  wizard_display_name             # 1 prompt
  wizard_project_type             # 1 prompt (node/php/custom)
  wizard_creds_volume             # 1 prompt, lists `claude-creds-*` volumes
  summary_and_confirm             # confirm-or-abort
  PROJECT_ID_ESC + DISPLAY_NAME_ESC  # sed-safe escapes computed once
  install_files                   # the orchestrator — see "Copy logic"
  generate_env                    # cp .env.example + sed in user values
  update_gitignore                # 13 entries appended (idempotent)
  set_exec_perms                  # chmod +x on the right files
  write_v2_marker                 # .configured-setup with VERSION="2.0.0"
  final_summary                   # styled "what's next" printout
```

Helpers are flat (no library imports) :
- `ask`, `slugify`, `titlecase`, `sed_escape`, `sedi` (portable in-place sed)
- `copy_verbatim`, `copy_templated`, `copy_dir`, `chmod_exec`

`set -euo pipefail` at the top — any error aborts the run with the
offending line in the trace.

## Templating model

**Two placeholders only** : `{{PROJECT_ID}}` and `{{PROJECT_DISPLAY_NAME}}`.
Replaced by sed at `copy_templated()` time. Used in :
- `devcontainer.json` (line 2 `name` + line 40 `window.title`)
- `.env.example` (line `#DC_PROJECT={{PROJECT_ID}}`, uncommented at runtime)

Everything else uses **shell expansion** at container runtime :
`${DC_PROJECT:-dc-project}`, `${CLAUDE_CREDS_VOLUME:-claude-creds-${DC_PROJECT}}`.
The `.env` file (generated by `generate_env()`) provides the values ;
the `:-default` fallbacks are neutral (`dc-project`) and never fire if
`.env` is correctly written.

### Why this matters

v1.3 had **11 sed placeholders** spread across 7 files. Maintenance
nightmare : adding a new field required updating both the wizard, the
sed substitution, and every file that referenced it. The v2 baseline
files use shell expansion natively (DC_PROJECT is read from `.env` by
both docker-compose and the lifecycle scripts) — so the installer's
sed surface shrinks to just the 2 cases that genuinely can't be done
via shell : the JSON `name` field and the commented `.env.example`
default value that needs uncommenting.

### Adding a new placeholder

If you ever need a third placeholder, the pattern is :
1. Add the value to the wizard (new prompt or derivation)
2. Add a `_ESC` line in `main()` : `FOO_ESC="$(sed_escape "$FOO")"`
3. Add a `-e "s|{{FOO}}|${FOO_ESC}|g"` clause to `copy_templated()`
4. Use `{{FOO}}` in the template file(s)

If a sed escape isn't enough (multi-line content, JSON nested
structures), prefer **jq** for JSON or **python** for YAML over
patching the sed surface.

## Copy logic

Three helpers, one orchestrator (`install_files`) :

| Helper | Use case | Behaviour |
|---|---|---|
| `copy_verbatim "$path"` | 90% of files | `cp $TEMPLATE_DIR/$path $DEST/$path`, `mkdir -p` the parent |
| `copy_templated "$path"` | The 2 templated files | sed-substitutes the 2 placeholders |
| `copy_dir "$path"` | 7 subdirectories | `cp -r $TEMPLATE_DIR/$path/. $DEST/$path/` |

The trailing `/.` in `copy_dir` is significant — copies *contents*,
not the directory itself. Avoids the cp-into-existing-dir surprise.

### File counts (current v2.0.0 baseline)

- 95 files in `templates/v2/`
- 93 files installed (the difference : `Dockerfile.base` ships in
  every install, but only ONE of `Dockerfile` / `Dockerfile.php` is
  copied per `PROJECT_TYPE`)

## Dockerfile selection

```bash
case "$PROJECT_TYPE" in
    node|custom) cp "$TEMPLATE_DIR/Dockerfile"     "$DEST/Dockerfile" ;;
    php)         cp "$TEMPLATE_DIR/Dockerfile.php" "$DEST/Dockerfile" ;;
esac
```

Both `Dockerfile` and `Dockerfile.php` already `FROM claude-devcontainer-base:${VERSION}`
in their content — no cat-assembly. Install.sh just picks the right
one. `Dockerfile.base` always ships alongside (it's the recipe used by
`initialize.sh` to build the base image — a separate artifact).

`node` and `custom` produce the same `Dockerfile` today. `custom`
exists as an explicit intent signal — "I'll edit this Dockerfile
myself, don't assume a project layer". If the generic Dockerfile ever
gets non-trivial Node defaults, `custom` can diverge.

## Detect-existing logic

Three cases for `$TARGET_DIR/.devcontainer/` :

| State | Action |
|---|---|
| Doesn't exist | Proceed (fresh install) |
| Exists, no `.configured-setup` marker | Treat as partial v2 → offer `[1] Reinstall / [2] Abort` |
| Exists, `.configured-setup` has `VERSION="2.x"` | Same as partial v2 → reinstall/abort |
| Exists, `.configured-setup` has `VERSION="1.x"` | **Abort** with pointer to Part 2 migration (not yet specced) |

The v1.3 abort path explicitly does NOT auto-migrate. The original
v1.3 `update.sh` (full-resync with diff) was deemed too fragile for a
major bump. Part 2 (deferred) will ship a Claude session prompt that
walks the upgrade per-file with human-in-the-loop validation.

## .env generation

```bash
cp .env.example .env
sedi -E "s|^#DC_PROJECT=${PROJECT_ID_ESC}\$|DC_PROJECT=${PROJECT_ID_ESC}|" $env
if [ -n "$CLAUDE_CREDS_VOLUME" ]; then
    sedi -E "s|^#?CLAUDE_CREDS_VOLUME=.*|CLAUDE_CREDS_VOLUME=${_esc}|" $env
fi
```

The full `.env.example` (all vars commented, with operator docs) gets
copied as-is. Then **just two lines** get mutated :

1. **`#DC_PROJECT=<PROJECT_ID>`** (templated, commented in the source)
   → **`DC_PROJECT=<PROJECT_ID>`** (uncommented, same value)
2. **`#CLAUDE_CREDS_VOLUME=claude-creds-shared`** (commented default)
   → **`CLAUDE_CREDS_VOLUME=<user-chosen>`** (uncommented), iff the
   user picked a shared volume in the wizard. Otherwise stays commented.

If `.env` already exists (reinstall path), it's **preserved** — never
overwritten. The user's `.env` may carry secrets, custom firewall
domains, EXTRA_NETWORK, etc.

## Exec perms

`set_exec_perms()` is explicit — no `find -name '*.sh' -exec chmod`
sweep. Reasoning : sweeping would also flip bits on shipped Python
files that happen to be importable but not directly executable, and
on host-helpers/ entries that aren't `.sh`-named.

The exhaustive list :
- Root `.sh` (9) : initialize, on-create, post-create, post-start,
  shell-init, install-extensions, init-firewall, firewall-mode,
  test-firewall, diag-ollama-local
- `firewall/` (3) : mitm-init.sh, firewall-blocks (extensionless),
  compile-policy.py
- `claude/` (1) : sync-creds.sh
- `claude-bridge/` (1) : healthcheck.sh
- `host-helpers/` (12) : the entire dir — all extensionless executables
- `skills/` (1 + variable) : sync-skills.sh, plus
  `skills/scan-deps/extract-auto-dependencies` and
  `skills/scan-deps/extractors/*` if present

If you add new executables to the v2 baseline, **update
`set_exec_perms` explicitly**. Don't rely on the sweep pattern.

## ANSI color escape gotcha

Colors defined as `BOLD=$'\033[1m'` (ANSI-C quoting) — the escape
sequence is interpreted at parse time, so the variable holds the
literal ESC byte.

**Wrong** : `BOLD='\033[1m'` (single quotes — backslash stays literal).
Heredocs (`cat <<BANNER`) don't interpret backslash escapes, so the
banner would show literal `\033[1m` characters in the terminal.

**Why `echo -e` works elsewhere** : `echo -e` interprets backslash
sequences at print time. But `cat`, `printf "%s"`, and heredocs
don't. ANSI-C quoting works everywhere.

## Wizard input

Four prompts, all read via `read -r -p "  [...]: " _var` :

1. PROJECT_ID — slug regex `^[a-z0-9]([a-z0-9-]*[a-z0-9])?$`
2. PROJECT_DISPLAY_NAME — free text, sed-escaped before substitution
3. PROJECT_TYPE — single digit `[1/2/3]` → node/php/custom
4. Shared creds volume — text or `n` / `no` / `none` for per-project

**Non-interactive mode** : drop. Use env vars + stdin piping for CI :
```bash
# Default answers (Node, no shared creds, confirm)
printf '\n\n\nn\n\n' | bash install.sh /path/to/target
```
v1.3 had `--non-interactive` flag ; it was untested and removed in v2.

### Why `read -p` prompts don't show in piped output

When stdin is a pipe (not a TTY), bash's `read -p` writes the prompt
to stderr — invisible in stdout-only captures. The first smoke test
of v2 was confused by this : I miscounted the pipe inputs because the
creds volume prompt didn't appear in the output. The fix : count
**reads**, not visible **lines**.

## TEMPLATE_VARIANT

```bash
TEMPLATE_VARIANT="${TEMPLATE_VARIANT:-v2}"
TEMPLATE_DIR="$SCRIPT_DIR/templates/$TEMPLATE_VARIANT"
```

`templates/` is plural by design — leaves room for `templates/v3/` or
`templates/minimal/` etc. Today only `templates/v2/` exists.

To ship a new variant :
1. `mkdir templates/minimal && cp -r templates/v2/. templates/minimal/`
2. Edit to taste (drop claude-bridge/, host-helpers/, prune the firewall...)
3. Document in CHANGELOG + README
4. Invoke with `TEMPLATE_VARIANT=minimal bash install.sh ...`

If multiple variants warrant a wizard prompt, add a 5th step in main()
before `install_files`.

## Templates refresh (sync from upstream baseline)

The `templates/v2/` directory is a **frozen snapshot** of the
project-of-truth's `.devcontainer/`. When that baseline evolves
(typically in the source project's rollout, here :
`plans/devcontainer-tools-v2-migration/`), `templates/v2/` needs a
manual refresh.

The canonical refresh procedure is documented in
[plans/devcontainer-tools-v2-migration/LOG.md § P1-S2](plans/devcontainer-tools-v2-migration/LOG.md)
under "Canonical templates/ refresh procedure".

Three-step pattern :
1. **Drop** the v2-dropped artefacts (gh-secure/, Dockerfile.node,
   master-review/, KNOWLEDGE.md single-file, test-db.php, etc.)
2. **Copy** the SCOPE.md in-scope files from `.devcontainer/` ; skip
   the excluded ones (`.local` skills, `capture_messages_debug.py`, etc.)
3. **Scrub** all project-specific identity references
   (ragnarok/cyro/portal42/<your-handle>) — match templates/v2/
   neutral patterns (`{{PROJECT_*}}`, `dc-project`, generic comments,
   `CLAUDE-project.md` stub)

No `sync-templates.sh` helper today — the refresh is rare enough
(once per rollout) that a documented bash block beats a script that'd
need to be maintained.
